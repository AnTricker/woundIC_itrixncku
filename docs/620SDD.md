# 620 SDD - BERTScore Calibration, Comparison Evidence, and VQA Dataset Plan

本文件依據 [620.md](./620.md) 整理本週需求。此文件是 implementation 前的 SDD，先定義目標、輸出、流程與風險，不直接開始改 code。

## 1. Background

前一階段已完成：

- local / SaaS simple smoke outputs。
- translation outputs。
- lexical score：`BLEU-4`、`ROUGE-L`、`METEOR-lite`、`CIDEr-lite`。
- grouped BERTScore script：`scripts/bertscore_rescore.py`。
- BERTScore report：`bertscore_comparisons.json` / `bertscore_comparisons.md`。

目前問題是：BERTScore 已能產生分數，但 report 還不夠能支持人工判讀與簡報說明。

劉博士希望看到的不只是分數，而是每張圖片實際丟進 BERTScore 的文字內容，例如：

```text
baseline English caption
translated baseline
candidate English caption
translated candidate
```

此外，也需要確認 BERTScore 是否被固定欄位或短詞彙拉高，避免把分數誤解為真正的 wound description quality。

## 2. Current Problem

### 2.1 Grouped Comparison 太多

606 階段原本設計五組 comparison：

| Comparison | Meaning |
|---|---|
| `a_vs_c` | reference English vs candidate English |
| `a_vs_b` | reference English vs translated reference |
| `c_vs_d` | candidate English vs translated candidate |
| `a_vs_d` | reference English vs translated candidate |
| `b_vs_d` | translated reference vs translated candidate |

620 需求調整為：本週 report 只保留 `AC` 與 `BD` 作為主要結果，避免 translation error 影響太多解讀。

新定義：

| Short Name | Comparison | Purpose |
|---|---|---|
| `AC` | `a_reference_english` vs `c_candidate_english` | 直接評估 caption generation result |
| `BD` | `b_translated_reference` vs `d_translated_candidate` | 對應人工主要閱讀中文時的 comparison |

`AB`、`CD`、`AD` 暫時不作為主要結果，只保留為 optional diagnostic。

### 2.2 缺少具體 Input Evidence

目前 report 有分數表，但不容易知道 BERTScore 實際比較了哪些文字。

需要新增 per-image evidence，讓 reviewer 可以看到：

- image filename
- wound category
- AC 的 reference text / candidate text
- BD 的 reference text / candidate text
- 使用哪些 caption fields
- visual summary only score
- visual summary + wound features score

### 2.3 BERTScore 可能被固定欄位拉高

目前 `caption_text()` 使用：

```text
visual_summary
wound_features
observed_supporting_features
```

但部分 wound features 可能是短欄位或固定詞，例如：

```text
not observed
irregular
red
moist
```

如果 visual summary 本身差異大，但 wound features 很像，整體 BERTScore 可能被拉高。

因此本週需要比較兩種 scope：

| Scope | Fields |
|---|---|
| `visual_summary_only` | 只使用 `caption.image_observation.visual_summary` |
| `full_caption_fields` | 使用既有 `caption_text()` 欄位集合 |

若兩者差距明顯，report 必須說明：

```text
BERTScore 可能被 wound_features / fixed short fields inflate。
```

## 3. Goals

### 3.1 Primary Goals

1. 調整 BERTScore report 的主結果，只呈現 `AC` 與 `BD`。
2. 新增 per-image BERTScore input evidence。
3. 對每張圖片顯示實際丟入 BERTScore 的 text。
4. 支援兩種 scoring scope：
   - `visual_summary_only`
   - `full_caption_fields`
5. 在 report 中比較兩種 scope 的差距。
6. 標記可能被 wound features 或固定短詞拉高的案例。

## 6. BERTScore Scope Calibration Plan

### 6.1 Scope A: Visual Summary Only

只抽取：

```text
caption.image_observation.visual_summary
```

用途：

```text
檢查模型核心自由描述是否接近 reference。
```

優點：

- 最接近人工快速閱讀 impression。
- 比較不會被固定欄位拉高。
- 容易在 report 中展示。

限制：

- 可能忽略 wound_features 中有用的細節。

### 6.2 Scope B: Full Caption Fields

使用目前既有 `caption_text()` 欄位：

```text
caption.image_observation.visual_summary
caption.wound_features.shape_pattern
caption.wound_features.edges_margins
caption.wound_features.wound_bed
caption.wound_features.color
caption.wound_features.texture
caption.wound_features.fluid_exudate_bleeding
caption.wound_features.periwound_skin
caption.category_specific_check.observed_supporting_features
```

用途：

```text
檢查整體 wound description fields 是否接近 reference。
```

風險：

- 固定短詞可能拉高分數。
- `not observed` 類型文字可能讓不同圖片看起來更接近。
- category-specific supporting features 若 prompt 模板固定，可能造成 score inflation。

### 6.3 Delta Interpretation

每張圖片與每個 comparison 都計算：

```text
delta_f1 = full_caption_fields_f1 - visual_summary_only_f1
```

解讀：

| Pattern | Meaning |
|---|---|
| `delta_f1` 接近 0 | full fields 沒有明顯拉高或拉低 |
| `delta_f1` 明顯 > 0 | wound features / fixed fields 可能拉高分數 |
| `delta_f1` 明顯 < 0 | wound features 加入後反而揭露更多差異 |

建議 threshold：

```text
abs(delta_f1) >= 0.05 => mark as noticeable
abs(delta_f1) >= 0.10 => mark as strong calibration difference
```

## 8. VQA Dataset Plan

### 8.1 Motivation

目前模型輸出是 caption。下一步可以把 caption 轉成選擇題，檢查 LLM 是否能根據描述判斷傷口類型。

例：

```text
Description:
There is erythema, superficial epidermal loss, rough texture, and redness.

Question:
Which wound category is most likely?

Choices:
A. abrasions
B. bruises
C. burns
D. cut

Answer:
A. abrasions
```

這可建立可量化的 VQA-style dataset，用來測試：

- caption 是否包含足夠分類訊息。
- LLM 是否能從 wound description 理解 wound type。
- 不同模型 caption 是否導致不同分類準確率。

### 8.2 Dataset Source

可從以下資料產生：

| Source | Use |
|---|---|
| local caption output | candidate-generated VQA |
| SaaS baseline caption | reference-generated VQA |
| translated caption | Chinese VQA / human-review VQA |
| original image category | answer label |

### 8.3 Output Format

建議 JSONL：

```json
{
  "image": "abrasions (27).jpg",
  "category": "abrasions",
  "source_run": "runs/20260525_gemma4_26b",
  "source_provider": "local",
  "source_mode": "simple",
  "caption_scope": "visual_summary_only",
  "question": "根據描述，最可能是哪一類傷口？",
  "choices": [
    "abrasions",
    "bruises",
    "burns",
    "cut"
  ],
  "answer": "abrasions",
  "evidence_text": "...",
  "language": "zh_tw"
}
```

### 8.4 First Version Rule

第一版先做 deterministic generation，不呼叫 LLM：

- question template 固定。
- choices 從 wound categories 抽樣。
- correct answer 來自 metadata target category。
- evidence text 來自 visual summary。

後續才加入 LLM-generated distractors。

## 10. Local Hardware / Model Plan

### 10.1 Hardware Baseline

本週的 autonomous / self-improvement 實驗必須以本機硬體為限制條件：

| Item | Current Plan |
|---|---|
| GPU | NVIDIA RTX 4090 |
| VRAM | 24 GB class |
| Runtime | local Ollama first |
| Primary use | caption generation, translation, prompt variant testing |
| Cloud use | Gemini only as fixed baseline or limited reference, not repeated heavy calls |

這代表 autoresearch-style loop 不能設計成大量雲端 API 或大型 full fine-tune。第一版必須是：

```text
single-machine
single-GPU
small smoke subset
local Ollama model
metric-gated prompt experiment
```

### 10.2 Local Model Candidates

目前已使用或規劃比較：

| Model | Role | Notes |
|---|---|---|
| `gemma4:e2b` | lightweight baseline / translator | 速度快，適合大量 translation 或 quick check |
| `gemma4:26b` | stronger local caption candidate | 已有 20260525 run |
| `gemma4:12b` | new middle-size candidate | 本週新增評估想法，可能是 4090 上較平衡的 prompt experiment model |
| `gemma3:12b` | fallback candidate if Gemma 4 12B is not in local Ollama | Ollama library 有 `gemma3` 12B family |

Model tag 必須先用本機確認：

```bash
ollama list
ollama show gemma4:12b
ollama show gemma3:12b
```

若 `gemma4:12b` tag 不存在，不應假設可直接跑；先改用本機可用 tag 或下載前另行確認。

### 10.3 Gemma 4 12B Notes

根據 Google AI for Developers 的 Gemma 4 overview，Gemma 4 family 包含 E2B、E4B、12B、31B、26B A4B 等大小；其中 12B 被描述為 unified multimodal model，支援 text / image / video，且 12B、E2B、E4B 有 native audio 能力。該頁也列出 Gemma 4 12B approximate inference memory：

| Precision | Approx. memory |
|---|---:|
| BF16 | 26.7 GB |
| SFP8 | 13.4 GB |
| Q4_0 | 6.7 GB |

對 RTX 4090 的意義：

- BF16 可能超過 24 GB VRAM，尤其還沒算 KV cache 與 runtime overhead。
- SFP8 / Q4_0 較可能可行。
- 若用 Ollama / GGUF，應優先測 quantized 版本。
- context length 越大，KV cache 越吃 VRAM，所以 autoresearch loop 要限制 prompt/context。

本週不直接承諾 Gemma 4 12B 一定可跑；先把它放進 local model candidate plan。

Source note:

- Google AI for Developers, Gemma 4 overview: <https://ai.google.dev/gemma/docs/core>
- Ollama Gemma 3 library fallback reference: <https://ollama.com/library/gemma3>
- Local availability still must be verified with `ollama list` / `ollama show` on this machine.

### 10.4 Model Comparison Rule

若本週要加入 12B 實驗，建議最小比較：

| Run | Model | Purpose |
|---|---|---|
| existing | `gemma4:e2b` | small / fast baseline |
| existing | `gemma4:26b` | stronger local candidate |
| new optional | `gemma4:12b` or `gemma3:12b` | middle-size tradeoff candidate |

比較項目：

- output token count
- total duration
- VRAM peak
- GPU utilization
- AC / BD BERTScore
- visual-only vs full-field delta
- VQA dataset category accuracy

## 12. Autoresearch Prompt Self-Improvement Plan

Autoresearch / self-improvement 方法已拆成獨立文件：

```text
docs/620autoresearch_prompt_ablation_plan.md
```

本週在 620 SDD 中只保留核心方向與引用，不把 autoresearch method 綁死在 healthcare、VQA、translation、schema 或 text-data 上。

核心想法：

```text
agent-driven self-improvement loop for prompt engineering
```

也就是讓 agent 讀取 previous records、分數、schema failures 與 per-image evidence 後，提出下一個 prompt 改良假設，產生小幅 prompt/schema/context variant，跑固定 local subset，再用 metric gate 與人工 evidence 決定 keep / reject / human review。

Ablation test 仍保留，但定位改為：

```text
self-improvement loop 中用來定位原因的 diagnostic experiment type
```

620 本週只需要保留以下 self-improvement record fields：

- objective
- hypothesis
- prompt component ID
- prompt variant ID
- local model tag
- smoke subset
- metric profile
- runtime profile
- failure analysis
- next hypothesis
- keep / reject / human-review decision

Healthcare domain knowledge、VQA dataset、translation、schema reduction、model selection 都應是未來可插拔 module，不應和 autoresearch method 本身混在一起。

## 15. Risks

| Risk | Impact | Mitigation |
|---|---|---|
| BERTScore 被固定欄位拉高 | 分數誤導 | 加入 visual-only vs full-field delta |
| Translation 品質影響 BD | 中文 review score 偏差 | AC / BD 分開呈現 |
| Evidence report 過長 | Markdown 難讀 | JSON 存完整，Markdown 只列 top examples 或可設定 limit |
| VQA choices 太簡單 | accuracy 虛高 | 後續加入相近類別 distractors |
| 自動 prompt loop 失控 | 改壞 prompt 或浪費 GPU | 第一版只設計，不自動覆蓋 prompt |
| Autoresearch 不適配本專案 | 方向錯誤 | 只借用固定 budget + metric gate 概念 |
| 4090 VRAM 不足以跑 Gemma4 12B high precision | local run 失敗或 context 太小 | 優先 quantized / Ollama GGUF；先 3-image probe |
| Gemma4 12B Ollama tag 不存在 | 不能直接測 | 先 `ollama list/show`；必要時 fallback `gemma3:12b` |
| 自動 prompt loop 過度依賴 BERTScore | prompt toward metric hacking | 加入 VQA accuracy、manual review、schema/token cost |
| domain knowledge prompt 太長 | context / VRAM cost 上升 | 先用 wound-type dictionary，不直接塞 textbook 長文 |
